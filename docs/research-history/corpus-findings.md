# F# evaluation corpus: measured repository comparison

Research date: 20 November 2026. Read-only shallow clones and source inventory were performed. No SDK restore, MSBuild evaluation, build, Ionide run, or memory/latency benchmark was performed.

## Recommendation

Use **dotnet/fsharp as the largest verified repository in this comparison**, **Grace as the application-style compatibility/performance corpus**, and **B2R2 as a large no-signature-file and generated-source stress corpus**. Do not advertise dotnet/fsharp as the globally largest public F# repository: ten plausible candidates were measured, not every public repository.

The distinction matters. dotnet/fsharp has the most total F# physical lines, but test fixtures account for most of them and its production source has extensive `.fsi` boundaries. B2R2 has more production-path F# lines and no `.fsi` files in its production-path inventory; generated opcode tables inflate some of that size but are real project inputs. Grace provides substantial ordinary .NET application code and libraries, with no production `.fsi` files in the inspected paths. A design that performs well on the compiler because of signature boundaries may still fail on Ben's monolith.

Concrete checked examples:

- B2R2 `VEXOpcodeMap.fs` is 62,980 lines; `LegacyOpcodeMap.fs` is 22,699. Their headers say the per-opcode functions are generated by IntelParserGen. Both appear as conditional `Compile` inputs controlled by `NoOpcodeMaps`. Benchmark the normal evaluated configuration and optionally a separately named generated-heavy slice; do not remove these files silently to improve results.
- aardvark.base `NativeTensorGenerated.fs` is 52,024 lines, a large fraction of that repository's F# total.
- Darklang `NormalizationData.fs` is 8,331 lines and explicitly says generated/do not edit.
- dotnet/fsharp's large fixture corpus includes deliberately invalid snippets and `ComparersRegression.fs` at 58,630 lines. Do not pretend all tracked test snippets form one valid F# project.
- Fable includes a substantial FCS fork. Using Fable as the sole secondary corpus would double-count much compiler-shaped behavior.

## SDK/build constraints to preserve

- **dotnet/fsharp:** inspected `global.json` pins `11.0.100-rc.3.26522.148`, allows prerelease, uses repository `.dotnet`, and pins Arcade/Helix SDKs. The development guide documents `./eng/common/dotnet.sh` followed by `dotnet build FSharp.Compiler.Service.slnx`. The root props intentionally set `BUILDING_USING_DOTNET`/`FSHARPCORE_USE_PACKAGE` for this solution. Preserve this context; do not replace its project model with a synthetic list of files. Compiler sources use many `.fsi` boundaries (225 `.fsi` under the production source-path inspection).
- **B2R2:** root `Directory.Build.props` targets `net11.0` and pins implicit FSharp.Core `11.0.101`. It had no root global.json in this checkout, so the benchmark harness must pin a compatible SDK explicitly. Production-path inspection found no `.fsi` files. Project conditions and generated opcode inputs matter.
- **Grace:** root `global.json` pins SDK `10.0.400` with `latestPatch`; the CLI targets `net10.0`, uses preview F# and graph-based/parallel compiler flags in project XML. It uses ASP.NET Core, Orleans and package references including NodaTime, a useful match to Ben's .NET application context. Source navigation/project cracking does not require launching Azure, Redis or the whole server. Full application integration tests do need their documented prerequisites and should not be conflated with extension evaluation. Production-path inspection found no `.fsi` files.
- **Darklang:** `backend/global.json` pins `11.0.100` with roll-forward disabled. Its backend solution, scripts and Docker/service environment add setup cost; retain as an additional application corpus if Grace is unrepresentative.
- **Fable:** root SDK `10.0.100`; compiler fork, multiple target languages, generated parser files and conditional compilation require controlled scope.
- **FAKE:** SDK `6.0.301`/latestMinor plus legacy framework targets and many small projects make it valuable for backwards compatibility, but less convenient as the first performance gate.
- **JetBrains F# support:** excellent semantic fixture source; tiny invalid fixtures inflate file count, while building requires the Rider/ReSharper SDK/Gradle setup. Use licensed regression fixtures selectively rather than requiring its whole IDE build for every benchmark.

No assumption is made that an installed FCS release supports the current compiler repo's latest syntax. Pin the benchmark compiler/FSAC/FCS compatibility explicitly; if a supported release branch is necessary, record the new commit and regenerate the inventory instead of reusing these counts.

## Proposed benchmark use

1. **Largest verified total / giant project:** pin dotnet/fsharp above; evaluate the FCS solution and benchmark queries spanning early/late compiler files, definitions, broad references, `.fsi`/`.fs` targets and public API edits.
2. **Real application gate:** pin Grace; use the solution and CLI/server projects for ordinary source navigation, references across SDK/shared/types, external hovers, linked source ownership, inferred public types, and multiple dirty buffers.
3. **No-signature and generated stress:** pin B2R2; benchmark both the 107-project solution and Intel project. Report generated-map time separately and include the normal configuration in total resource accounting.
4. **Semantic edge regressions:** use small hand-written oracle fixtures plus relevant FSAC/compiler/JetBrains tests, with proper licenses and expectations. Do not manufacture a single huge fake project from unrelated invalid snippets.

Include cold no-cache opening, warm restart, first exact query, warm query, early-file edit invalidation, broad references, cancellation and worker recycling. Count all child-process RSS and time to complete correct results. Repository size inventory alone does not establish any memory or latency result for the proposed extension.

## Reproduction and artifacts

`research/corpus/measure_corpus.py` is a standalone read-only Python inventory script using only the standard library and Git. It counts tracked regular-readable F# files and records category rules, exact duplicate contents, generation-marker candidates and static project includes. It does not execute repository code. `research/corpus/metrics.json` holds the complete results, including per-project includes and generation markers; `inventory.json` is the earlier top-directory inventory.

From `/workspace/scratch/dd9aeba5da3c`:

```sh
python3 research/corpus/measure_corpus.py \
  research/corpus/fsharp research/corpus/B2R2 research/corpus/Fable \
  research/corpus/Grace research/corpus/dark research/corpus/aardvark.base \
  research/corpus/resharper-fsharp research/corpus/FAKE \
  research/FsAutoComplete research/corpus/Paket
```

Clone the original repository and check out the exact SHA before rerunning. Counts exclude untracked build-generated files and Git submodule contents unless separately cloned and inventoried. The script is an inventory tool, not extension implementation; Rust remains the preference for the product engine and CLI.
